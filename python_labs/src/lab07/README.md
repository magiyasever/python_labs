# Отчет по лабораторной работе №7

## Алгоритмы поиска

- `linear_search(nums, x)` — линейный поиск;
- `binary_search(sorted_nums, x)` — бинарный поиск в отсортированном списке;
- `two_sum_brute(nums, target)` — перебор всех пар;
- `two_sum_fast(nums, target)` — один проход со словарём.

| Алгоритм | Сложность |
|---|---|
| Линейный поиск | O(n) |
| Бинарный поиск | O(log n) |
| two_sum_brute | O(n²) |
| two_sum_fast | O(n) |

## Алгоритмы сортировки

- `bubble_sort(nums)` — сортировка пузырьком с ранним выходом;
- `insertion_sort(nums)` — сортировка вставками;
- `selection_sort(nums)` — сортировка выбором;
- `merge_sort(nums)` — нерекурсивная сортировка слиянием;
- `counting_sort(nums, lo, hi)` — сортировка подсчётом для заданного диапазона.

| Алгоритм | Сложность |
|---|---|
| Пузырьковая | O(n²) |
| Вставками | O(n²) |
| Выбором | O(n²) |
| Слиянием | O(n log n) |
| Подсчётом | O(n + k) |

## Вывод


При увеличении размера списка с 1 000 до 10 000 элементов пузырьковая сортировка замедлилась примерно в 121 раз, сортировка вставками — примерно в 122 раза, сортировка выбором — примерно в 101 раз: это соответствует квадратичной сложности `O(n²)`.

Для `sorted` рост составил около 18 раз в данном запуске,

а для `merge_sort` — около 5 раз; на таких маленьких размерах сильно влияют накладные расходы и шум замера. При переходе от 10 000 к 100 000 элементов `sorted` замедлилась примерно в 14 раз, а `merge_sort` — примерно в 12 раз, что близко к теоретической оценке.

На практике результат зависит от реализации, процессора и конкретных данных, но асимптотика `O(n log n)` растёт значительно медленнее квадратичной.

Сортировка подсчётом на миллионе чисел из диапазона [0, 100] оказалась примерно в 2.7 раза быстрее `sorted`, потому что диапазон значений намного меньше количества элементов.

Бинарный поиск сам по себе очень быстрый, но применим только к отсортированному списку. Сортировка стоит примерно как 7 линейных поисков, поэтому для небольшого числа запросов она может быть неоправданной, а при 10 000 запросов связка «сортировка + бинарный поиск» оказалась примерно в 720 раз быстрее линейного поиска.

В задаче `Two Sum` перебор пар при росте списка в 10 раз замедлился примерно в 106 раз, а решение со словарём — примерно в 11 раз; при 10 000 элементах решение со словарём быстрее перебора примерно в 2 000 раз.

Проверка `check.py` подтвердила корректность всех пяти сортировок, двух алгоритмов поиска и двух решений `Two Sum`: расхождений на 100 случайных тестах для каждого набора не обнаружено.
